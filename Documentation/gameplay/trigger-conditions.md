# Selecting conditions and handling known exceptions

Read [trigger design](triggers.md) first. The [native template/property reference](trigger-condition-reference.md) supplies all 91 direct-Condition templates, exact field layouts and serialized defaults; [datasets](trigger-datasets.md) supplies their vocabulary. [Audit evidence](../reference/trigger-audit.md) records source locations, hashes, classifications and remaining limits. Property names, template names and quest-objective names differ.

## Choose by the question you need to answer

| Question | Candidate / required context |
| --- | --- |
| Always / never / elapsed interval | ConditionAlwaysTrue, ConditionAlwaysFalse, ConditionTimer. Timer begins when that condition becomes eligible in the reported nested pattern; do not assume every nested timer starts at registration of the outer asset. |
| Is a feature currently unlocked? | ConditionUnlocked / property ConditionUnlocked, UnlockNeeded. Missing GUID is treated as unlocked; negate a presence guard for removable mods. |
| Any/all unlocks from a list? | Template ConditionUnlockedList / property **ConditionUnlockList**, UnlockNeededList/Item/UnlockNeeded, UnlockRangeOP. Choose its dataset value explicitly; default is None. |
| Population, owned buildings, goods, counts since registration? | ConditionPlayerCounter: choose PlayerCounter, Context, ComparisonOp, CounterAmount and CounterScope together. |
| Was an event emitted? | ConditionEvent with the exact SimpleEventType token and event-specific ContextData/ContextAsset. Listener registration order matters. |
| Is a session currently active? | ConditionActiveSession. For loaded/unlocked state use the corresponding audited event/feature; these are different questions. |
| Diplomatic state / discovery / reputation? | ConditionDiplomaticState, ConditionIsDiscovered + ParticipantRelation, ConditionReputation + ParticipantRelation. Source/target direction and dynamic-owner flags differ. |
| Is an object near another / selected? | ConditionObjectPosition + ObjectFilter + ObjectTargetFilter; ConditionObjectSelected + ObjectFilter. Audit owner/session flags and local UI implications. |
| Goods/items in storage? | ConditionInStorage + ObjectFilter; cargo slots, not equipped sockets in Serp's tests. |
| Multiple requirements on the same island? | Main ConditionMutualAreaInSubconditions with Area-scope PlayerCounter siblings; special propagation/timing limitations below. |
| Current quest state / a quest from a pool running? | ConditionQuestState, ConditionQuestPoolQuestRunning. Explicit states, quest/line GUID and range policy are required. |
| Item activation/socketing / buff active? | ConditionItemUsed (schema-only in this extraction; inspect custom template/example), ConditionIsBuffed for compatible active buff state. Neither proves passive socket effects. |
| DLC / creative / multiplayer / tutorial? | Corresponding ConditionIs* template. Coop with one human participant still differs from single player; use reviewed SingleHuman helper where that is the real question. |
| Specialized productivity, season, palace, Hacienda, modules or research check? | Find the relevant entry in the complete native index, then audit its consumer. A native achievement example is not proof of suitability as a mod's live TriggerCondition. |

Native `ConditionIsParticipantInGame/InGameParticipant` is described as checking game-setup selection. It is **not a reliable live existence/defeat predicate**. Pirates may remain true after destruction; already-registered tests may not update when another session is entered. LaFortune tests failed until re-registration/context changes. Use PirateDefeatHelpers or an audited lighthouse/owned-object counter for the specific pirate lifecycle. For defeated humans use the shared processing-human-loss check; a remaining ship is insufficient. `ConditionMetagameLoaded/HumanPlayerCount` counts Coop humans in the notes, so use SingleHuman's slot checks instead of equating it with participant-slot count.

## PlayerCounter contracts and pitfalls

The exported defaults are ObjectBuilt, Context=0, AtLeast, Global, CounterScopeUseCurrentContext=1, CounterScopeContext=0, CounterScopeKeepFirstFound=1, CounterValueType=Current, CheckedParticipant=Human0. **CheckedParticipant is only enabled by CheckSpecificParticipant=1**; its default token does not mean every counter checks Human0.

- ObjectBuilt reports current owned-object count in Serp's tests. RelativeToQuestStart also works from trigger registration and can become negative: after removing two matching buildings you must build three to achieve a delta of one. It is not a construction-event accumulator. ObjectDestroyed/ObjectLost did not count demolished buildings in those tests.
- Select Context for the counter's meaning: PopulationByLevel needs the population GUID; WorkingConditions also needs population, not workforce. A PlayerCounterContextPool is a supported workspace technique for compatible modded populations/objects. Plain PlayerCounter pools sum members; they do not mean "every member meets the threshold". Quest StatusQuo's CheckAnyPoolAsset/CombinePoolAssets rules belong to that objective and cannot simply be added to TriggerCondition.
- CounterScope and CounterScopeContext select Global, Region, Session or Area as allowed by the dataset. CurrentContext, ActiveSession and KeepFirstFound have different roles; default KeepFirstFound retains a discovered context according to the schema. Do not silently assume a repeating trigger keeps following the latest active session.
- Counters checking dead/nonexistent CheckedParticipants were always false in shared_PlayerKnownAndInGameCheck, regardless of comparison, including zero checks. Its AI/first-party persistent FeatureUnlocks are explicitly unsuitable as updated liveness checks; that source recommends the processing-owned-object pool 1500003867 for an AI-alive check.
- Third-party counter queries need ProfileCounter on the targeted profiles. BT Passive Trading/Quests add it; it is not safe to assume every merchant has that property. Adding ProfileCounter does not fix unrelated ShipsInRange/item-insertion limitations.
- Lua ProfileCounter queries cannot use pools according to the notes. The established workaround is a predefined XML pool condition queried through `ts.Conditions.GetCurrentConditionAmount(TriggerGUID)`, with the helper and pool audited. This is not a new arbitrary Lua pool-query API.

## Area, session and object propagation

**Serp test / qualified workaround:** Area-scope PlayerCounter traverses islands owned by the **processing participant**. CheckedParticipant changes the object-owner test, not the traversed islands. This explains apparently false AI/foreign-island checks. Lua counter APIs with an explicit AreaID have a separate contract.

For dynamic-session spawning, the reported reliable arrangement keeps Area-scope PlayerCounter as the **main condition at the level owning the spawn action**, uses a qualifying building, and sets CounterScopeUseCurrentContext=0 when selecting a matching area. SessionFilter AllowQuestSession=1 plus AllowQuestArea=1 can carry the selected session without hardcoding GUIDs. This does **not** make LimitToQuestArea work in an ordinary trigger.

The notebook first claimed a helper quest was unavoidable, then found the trigger-only session technique. Preserve the later result and its boundaries: another counter may overwrite area context; branched/nested forms were inconsistent; ActionExecuteActionByChance combinations failed when the counter was moved away from the direct main condition. A separate context-producing trigger with ActionRegisterTrigger/InheritArea=1 worked in some flows, but an intervening ConditionTimer failed in a recorded spawn test. Do not add delay nodes to that propagation path without checking a matching example.

For **island restriction**, CodeSnippets' human area-buff workflow starts a helper quest with InheritQuestArea and GetQuestSessionFromArea, or registers a trigger from that quest with InheritArea. LimitToQuestArea/CheckQuestArea rely on that quest context in the reported examples. They do not restrict arbitrary units as if they were buildings, and LimitToQuestArea excludes water/buildable-land-external targets. Quest-based workflows cannot be transplanted to AI. The Outdated_AreaBuffsHelper example is historical; the current CodeSnippets describe a more complete human workflow and complicated AI marker/brute-force workaround.

**Coop context is not uniform:** HowTo.xml:1121–1123 reports UseCurrentSession and CounterScopeUseActiveSession taking the Coop leader's session, while ConditionActiveSession becomes true when any Coop peer is there. Those findings do not establish which session a later action receives. Match the exact flag and consuming filter instead of treating all "active/current session" checks as interchangeable.

**Quest-linked objects:** HowTo.xml:1142–1152 reports quest actions registering a trigger with LinkAllQuestActionsToQuest and LinkAllActionsToQuest, whose spawned objects then qualify for ObjectRestrictToQuestObjects. Serp explicitly confirmed on 2026-10-03 that it remains **unclear whether both flags are required or one suffices**. The observed combined setup does not establish either flag individually as sufficient. This does not make arbitrary preexisting/selected/sold objects quest objects. The notes restrict this filter to objects spawned within the quest or quest line and recommend an explicit ObjectGUID to avoid including the quest's starter object, such as its lighthouse. LinkAllActionsToQuest alone did not fix ordinary trigger island restriction. Preserve the separate linking, object identity and area contracts.

**ConditionMutualAreaInSubconditions:** tested as a main condition, with area-producing siblings at the **same level**. Serp reports it did not fire when placed inside a subtrigger. Serp assessed the original simultaneous-subconditions comment on 2026-10-03 as **very likely correct, not absolutely certain**: this special arrangement requires simultaneous subconditions rather than ordinary remembered Parallel completion. Use marker buildings to represent whether an area buff/item has been applied when XML cannot detect the socketed state. Matching areas does not by itself give arbitrary actions QuestArea semantics. Retain the very-likely qualification for the timing exception; no new game test was performed.

ObjectUseParentConditionObjects is explicitly marked incompletely implemented in the native ObjectFilter schema. Serp's tests failed with PlayerCounter, ObjectBuilt event, ObjectPosition, ObjectSelected and HP-check conditions, including a TutorialInteraction attempt. Do not assume it identifies the matching object. Prefer an explicit audited ObjectFilter or a helper identity/quest-object design; distinguish asset GUID from instance OID.

ObjectPosition is a reported better alternative to ShipsInRange for pool/proximity checks. Pirates Flak Trigger records ShipsInRange's problems with third-party trader ships, specific GUID versus pool switches, automatic registration/session context and owner checks. It manually registers the conditions and enumerates airships. Do not copy it as a general pool-safe proximity recipe.

**Pool consumers differ:** HowTo.xml:1176–1191 reports PlayerCounterContextPool and ItemEffectTargetPool working in trigger ObjectFilter, including nested membership in a custom AssetPool, but not in MatcherCriterionGUID/UnlockAsset consumers requiring ordinary AssetPool entries. The same notes correct an earlier claim about one-member pools: a single-entry AssetPool failed with ActionDeleteObjects/ObjectGUID, and a single-entry PlayerCounterContextPool also failed **in ObjectFilter**, while that does not establish failure of ordinary PlayerCounter counting. Inspect the consumer and retained correction before replacing one pool kind with another.

## Events, UI and quests

An event listener must be armed **before** the event. ConditionEvent GUIDLocked after an earlier unlock/lock operation can miss it; Campaign/Story comments also report a same-time registration/lock miss. A persistent ConditionUnlocked can be order independent for state, but it cannot substitute for a required future edge or avoid the missing-GUID/removal issue by itself.

| Event / condition | Observation and limitation |
| --- | --- |
| SessionEnter | Established recurring human lifecycle signal. May fire on save load as well as switches. Use a reset and guard heavy work. |
| SessionLoaded | Session loading is global and can precede a human visiting/unlocking it. Do not confuse with the separate default enum token SessionLoad. Verify spelling in SimpleEventType. |
| IslandSettled | Also fires on acquisition and initial settled islands in the notes. The executing Lua client need not be in that session. |
| ObjectBuilt | Does not fire for projectile SpawnImpactObject in the recorded tests. A current-object counter may be suitable, but owner/profile/creation route still matters. |
| HostileTakeoverCompleted | Reported for the participant losing the island. |
| QuestSuccessfullyResolved + ContextData | Worked in a documented setup; QuestStarted did not. Serp clarification2026-10-03: pool start versus ActionStartQuest remains a **reasoned hypothesis, not further tested**. Do not treat pool start as a proven fix or interchange ContextData and ContextAsset without a native/example match. |
| PirateResettled / participant removal events | Notes could not select a specific pirate with ContextAsset; removal events were insufficient for pirate-defeat tracking. Use the specialized helper. |
| ObjectAttached / ObjectDropped | Towing experiment reports Attached failed and Dropped worked. The mod is marked "will not work"; this is not a production towing recipe. |
| RuinStateEntered/Ended, AssetFileChanged | Did not work in the recorded rebuilding/mod-refresh cases. |
| MetaGameLoaded / ProfileLoaded | Conflicting and inconsistent save-load behavior, especially same-process reloads. A completed event and ConditionMetagameLoaded's state check are different mechanisms. Use reviewed lifecycle helpers. |
| GUIEvent / EnterUIState / LeaveUIState | GUIEvent was more reliable for selected UI states, but still local. LeaveUIState can also fire when leaving the loading screen. |
| TextPopupClosed | Filters layout flags, not a specific text GUID. Several letters with one layout can satisfy it. Story Coop replacements use the actual show/register sequence. |
| NotificationRemoved / MovieFinished | May mutate saved trigger state differently between peers. Successful money-only tests do not certify unlocks, other GUIDs, FeatureUnlock or starting the movie at another time. |

Keep quest preconditions in the quest with KeepCheckingPreconditionsWhenRunning when they must cancel it during execution. Pool preconditions only control later grants. ActionStartQuest ignores ordinary start preconditions in the notes, but running-precondition checking still applies. ResetPreconditionsAfterQuestWasTriggered resets event-like preconditions, not an engine guarantee that MetaGameLoaded emits on every reload.

QuestSessionDependencies is an OR among loaded sessions, not "all sessions loaded". ConditionQuestState should use exact flags and quest/line identity; Lua IsActive can remain true after completion, so the reviewed helper also checks not HasEnded. StateReached/StateReachable observations concern quest stages, not generic live spatial state. Same QuestDecision identities in concurrently active copies can propagate MP choices. Inspect the [personal evidence](../reference/personal-test-evidence.md) before selecting an objective helper.

## Numeric text sources, storage, buffs and item activation

**ConditionEvaluateTextSource:** schema declares numeric comparisons, but Serp reports numeric results becoming true irrespective of ComparisonType/ComparisonValue. Boolean-returning commands were usable in those tests. This is a schema/runtime discrepancy, not permission to invent expressions for arbitrary numeric checks. The native captured example is explicitly disabled tutorial content.

**ConditionThreshold:** Serp explicitly reaffirmed on 2026-10-03 that **all comments in CodeSnippets.md:702–710 remain current**, with their original certainty. Actions executed **23 times** in the recorded intended-single-execution test; ResetTrigger appeared never true, and placing Threshold in a SubTrigger hung new-game/save loading. Meta-storage usage appeared usable, area building counts required IsAreaSpecific=1, and the ProfileCounter text-source setup appeared not to work. ThresholdDuration=0 appeared usable; positive durations working and milliseconds as the unit remain **probable, not confirmed**. Do not silently promote any original "seems"/"likely" finding into certainty or universalize the exact 23 count to every context. Do not use Threshold as a drop-in fix for EvaluateTextSource. Prefer native counters for supported quantities, or an established Lua/lock bridge; keep an isolated Threshold workaround's limits beside its example. No new game test was performed.

**ConditionInStorage:** tests detect cargo/storage slots, not equipped sockets. Missing target amount zero can satisfy a zero comparison; require an independent object-existence gate when absence must fail. Multiple InStorageGoods entries and comparison policy must follow the native schema, not invented AND semantics.

**ConditionIsBuffed:** did not detect passive socketed/global VehicleItem effects even after adding Buff in Serp's test. The native examples use ActiveBuff; UseEffectHandler has its own BuffFactory/ForwardBuff/AreaBuff description. Do not generalize one failed ship test to every compatible active buff or generalize native ActiveBuff success to passive socket effects. The trading speed-buff mod instead reapplies periodically. Area-buff examples use marker buildings for socket state.

**ConditionItemUsed:** property exists but no same-named vanilla template is in the 91-entry index. Inspect the mod's custom template/embedded definition. ItemNeedsActivation distinguishes equipping from equipping-and-activation; shooting items did not trigger it in Serp's tests. ItemActionCompleted also failed in the recorded setup. Neither is a general projectile event detector.

Further recorded limitations: ConditionIslandsWithFertility Area did not satisfy the test and is not a per-island fertility predicate; Serp confirmed on 2026-10-03 that HowTo.xml:1844–1848 is the latest known state: ConditionAttractiveness/CountAllTypes interpretation remains uncertain and the suggested PlayerCounter/Attractiveness alternative is not newly confirmed; Serp clarified on 2026-10-03 that ConditionCorporationDifficulty **probably does not work in multiplayer**, with no further tests and no newly established Coop-versus-multiple-participant distinction. Retain these qualifications and consult their fields and exact source before choosing an alternative.

## Action-side special cases that affect trigger design

- ActionTriggerPopup on an auto-registered trigger showed on every peer once even when they had not executed that trigger. The popup helper manually registers after initialization. Multiple Coop registrations/late confirmations also queued duplicate popups; the WIP solution used distinct FeatureUnlocks, shared availability/cooldown and coordinated queuing. It remains WIP, not a general replacement for all GUI events.
- ActionAddGoodsToItemContainer could not populate an object spawned by the **same trigger**, even with an in-list delay. Serp uses a separately registered post-spawn trigger. HowTo.xml:1857 says third-party ships may need **two full trigger executions**, not merely two actions. Serp confirmed on 2026-10-03 that this is the latest known state, with no newer findings; the need/cause remains tentative rather than a guaranteed two-pass fix. For those recorded cases, NPC trading-station insertion failed. ActionDeleteItem had a different result, so do not generalize all inventory operations.
- ActionSpawnObjects SpawnGUID and ConditionObjectSpawnedObject ExecutionObject accept/declare pools in some contexts, but their random AssetPool choices caused MP desync in Serp's tests. A declared supported target type does not imply MP safety.
- AllowProcessingSession spawning failed in OnQuestEnd but worked in other quest contexts; AlwaysTrue could run before session entry. Use the actual quest/action lifecycle, not just an added delay.
- ConditionReputation checks the target's opinion of source in Serp's examples; ActionAddReputation changes processing's opinion of target. Third parties cannot simply become processing. LuaLight's reputation bridge is the established workaround and executes its synchronized code on all required humans.
- Multiple participants can satisfy a world-object check before a side effect/counter update becomes visible. A global `AtMost=0` guard alone did not prevent four spawns in a recorded four-player setup. A single Human0 coordinator is used in PirateComebackFix, including its deliberate behavior after Human0 defeat. Do not promise an arbitrary global check is atomic.
- The smallest GUID among still-registered triggers unlocking an asset supplied its displayed unlock requirement in Serp's tests, regardless of registration order. Unhide and unlock are separate actions/states. A deliberately never-completing display trigger is used in the building-limit example; do not copy its obsolete Threshold mechanism without its limitations.
- Diplomacy/SpecialTrigger, Reactions, achievement tracking and infotip VisibilityElement conditions are different consumers. Their priorities, chance fields or UI expressions are not SubConditionCompletionOrder. Review those systems separately before transferring a superficially similar rule.

The source-comment register keeps the original wording and source positions for the remaining contextual examples. Known unsuccessful approaches are evidence to avoid a trap; they are not missing instructions to finish implementing that experimental mod.
