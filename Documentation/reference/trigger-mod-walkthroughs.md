## 1500003013 — BT Passive Trading

**Classification: explainable; parent gating and exclusive branch priority confirmed by Serp.** Original source: `BT Passive Trading (Serp)/data/config/export/main/asset/MoreTradeForHumansArchi.include.xml:24` [GitHub](https://github.com/Serpens66/Anno-1800-Mods/blob/88821b04ee972424667178d35a5080a753a853d0/Recommended-Mods/BT%20Passive%20Trading%20%28Serp%29/data/config/export/main/asset/MoreTradeForHumansArchi.include.xml#L24). Full workspace-relative path and hash: [case register](triggers/mod-cases/cases.json). Owning template is Trigger, no BaseAssetGUID; inserted next to native 130221. AutoRegisterTrigger is inherited as 1; UsedBySecondParties is explicitly 0.

1. The main PlayerCounter looks for at least one current object of mod GUID 1500000041 owned by Blake. Native profile 45 is Archibald Blake; the mod adds ProfileCounter at assets.xml:67–70. The ship derives from native TradeShip 100438; its three human-capacity variants derive from 1500000041.
2. The child ConditionObjectPosition checks Blake's base ship within Radius=115 of pool 193897, with both target-owner enabling flags set to select the processing participant's kontors/piers. The pool's nested native members/base chains were followed; it is an ItemEffectTargetPool, not an individual harbor.
3. The condition sets **its children's** mode to MutuallyExclusive. In order, unlock 1500003072 chooses ship 1500003009, 1500003071 chooses 1500003005, and 1500003070 chooses 1500003001. These variants have different ItemContainer values; native/shared property membership was checked. In the mod's default configuration TradeBuff2 is an AlwaysTrue FeatureUnlock, while TradeBuff1/3 are AlwaysFalse; another integration can change those signals.
4. Each branch schedules the GUID change after 1000 ms. Source comment at line 21 explains that an immediate change made the opening counter false before completion and prevented reset. This matches [action side effects and completion](../gameplay/triggers.md#registration-repeat-execution-and-initialization).
5. The ResetTrigger is a nested chain of three **negated** ObjectPosition checks for the three variants, then restores each variant to base GUID 1500000041. It waits for none of the variants to be near this processing participant's ports. ExpectObjectExists/ExpectTargetExists are explicitly 0; this is not a requirement that three distinct variant ships exist. Root reset actions wait for that reset tree's completion under the documented pattern.

The GUID-change actions have ObjectFilter GUID/owner but **no radius and no ObjectUseParentConditionObjects**. Their target is not automatically the object matched by the parent condition. The integration supplies the missing invariant: assets.xml:544–547 explicitly prohibits using a ship GUID twice for a merchant in the same progression; its TradeFleet entries set Amount=1. Thus a broad owner/type filter is deliberate for that configuration. It is not an interchangeable recipe for several identical ships or an arbitrary new fleet mod. Overlapping player harbor radii are an explicitly accepted source limitation at MoreTradeForHumansArchi.include.xml:12–19.

**M001 answered by Serp, 2026-10-03:** ConditionObjectPosition is the parent gate. No subordinate trigger executes before it is true. MutuallyExclusive selects only the first matching complete branch from top to bottom; it does not bypass that gate. Serp explicitly confirms the GUID changes occur only within Radius=115. This resolves the documented recommendation despite the contrary native description retained in the field reference. It is an author-confirmed observation/rule, not a newly performed game test.

## 1500003820 — shared_PirateExtraSpawn

**Classification: explainable registration chain; continuous timer behavior remains open.** Source: `shared_PirateExtraSpawn/data/config/export/main/asset/SpawnShipsIfWeak.include.xml:17` [GitHub](https://github.com/Serpens66/Anno-1800-SharedMods-for-Modders-/blob/3aece64f299365309aaf1f7a57f28e2f6900f106/shared_PirateExtraSpawn/data/config/export/main/asset/SpawnShipsIfWeak.include.xml#L17).

The tree is processing-human discovery of Harlow → custom Harlow_Currently_NOT_Defeated → Harlow owns at most three objects from pool 700138 → Timer=3600000 ms → four ActionRegisterTrigger calls for 1500003835 at offsets 0, 500, 1000 and 1500 ms. After completion the embedded ResetTrigger waits 30000 ms before rearming. AutoRegisterTrigger=1 and UsedBySecondParties=0; there is no Human0 coordinator in this definition.

The custom condition is not a native template and is not an IsParticipantInGame check. The bundled helper's templates.xml:31–38 maps it to **positive unlock 1500001145**. That FeatureUnlock checks Harlow's lighthouse 100707 exists and has RuinCount at most zero, explicitly in session 180023. It self-unlocks, then uses a reset listener for the opposite 1500001147 signal to relock itself. The paired defeated state checks RuinCount at least one and resets on the positive not-defeated signal. Both begin locked, distinguishing initialization from a checked defeated/not-defeated result. Native profile 73 contains ProfileCounter; the actual lighthouse and session owners were inspected. The helper is bundled despite PirateExtraSpawn's metadata using LoadAfterIds rather than ModDependencies for its ID.

Native 700138 is a PlayerCounterContextPool containing the four pirate ship types 102429–102432; their base WarShip records were followed. This counter sums compatible members; it does not require each kind to meet a separate threshold. The source's extra-spawn workflow is distinct from its older diversity trigger in assets.xml. The metadata's "every 20 minutes" description concerns that other workflow, whereas this selected timer is one hour plus its reset wait; it is not evidence that this timer should be changed to 20 minutes.

The deepest actions register a short-lived script-dispatch trigger rather than directly repeating ForceBuild within one Lua call. forcebuild_harlow.lua:3–7 reports one build per game tick. ActionExecuteScript still runs on all human clients. Serp clarified on 2026-10-03 that the claimed multiplayer usability requires every client to call ForceBuild in **exactly the same tick**: direct one-call scripts, repeated via separate ActionExecuteScript invocations, are relatively practical under that premise. This is an author assessment, not a newly supplied controlled MP test or general scheduling guarantee. Once-per-tick throttling alone does not prove same-tick execution across peers. The script uses SessionParticipants, not the XML counter's Global scope; its different-session behavior remains unestablished by this answer. See [multiplayer contract](../multiplayer/synchronization.md#command-specific-behavior).

**M002 answered with uncertainty by Serp, 2026-10-03:** a full timer restart is **probable, not confirmed** if a preceding condition becomes false in the meantime. Applied here, exceeding three pirate ships probably discards the elapsed hour and starts a fresh 3600000 ms when the preceding gates become true again. Pause/resume is not established either. The source comment about aborting and KeepTimerOnUnregister do not prove the exact interruption contract. No new test was performed.

## 1500003835 — shared_PirateExtraSpawn

**Classification: dispatch structure explainable; owning-main optionality assessed by Serp, later XML registration explained by completed-versus-active state.** Source: `SpawnShipsIfWeak.include.xml:438`; the explanatory comment is at line 437.

AutoRegisterTrigger=0 and UsedBySecondParties=0 make this a manually armed trigger. Its callers include the four calls from 1500003820 described above. Its discovery condition and its custom positive not-defeated child both carry IsOptional=1. The child's only action executes `data/scripts_serp/forcebuild_harlow.lua` [GitHub](https://github.com/Serpens66/Anno-1800-SharedMods-for-Modders-/blob/3aece64f299365309aaf1f7a57f28e2f6900f106/shared_PirateExtraSpawn/data/scripts_serp/forcebuild_harlow.lua); that file exists in the same package. It selects ParticipantID 17 (Harlow in the audited ParticipantID dataset) and calls `ts.SessionParticipants.GetParticipant(Pirate_PID).Trader.ForceBuild()`. The notes report this building a pirate WarFleet ship, with the trader's remaining maximum constraining what is built. Native 73's WarFleet types are members of audited pool 700138.

This definition has no explicit ResetTrigger. Its repeated use depends on later manual registration, so it cannot be justified solely by the embedded-reset recipe. The caller's 500 ms spacing and the source's one-build-per-tick observation explain why this was separated from one coroutine spawning several ships. The default main/child completion mode is Parallel; neither IsOptional flag is a MutuallyExclusive selection.

**M003 clarified by Serp, 2026-10-03:** Serp thinks IsOptional matters only when a parent condition exists, matching the property description. On this owning ConditionIsDiscovered it therefore has no effect and is harmless. This is an author assessment, not a controlled test. Discovery remains the parent gate; its optional not-defeated child does not need to block completion, but its Lua action still requires a satisfied child. In particular, top-level IsOptional is not evidence that failed discovery consumes the trigger. The original line 437 comment is preserved but this broader consumption interpretation is not recommended. Serp's follow-up confirms that later XML registration can start it again after full completion, but does nothing if the instance is still registered (including waiting for discovery). Lua concurrent registration is a separate mechanism; see [Q005](discrepancies.md#q005-trigger-composition-and-registration-boundaries).

## 1500001103 — PirateComebackFleetFix

**Classification: explainable conditional cleanup; inherited register/reset runtime limits remain explicit.** Source: `P PirateComebackFleetFix (Serp)/data/config/export/main/asset/ComebackFleet.include.xml:131` [GitHub](https://github.com/Serpens66/Anno-1800-Mods/blob/88821b04ee972424667178d35a5080a753a853d0/YouKnowWhatYouDo-Mods/P%20PirateComebackFleetFix%20%28Serp%29/data/config/export/main/asset/ComebackFleet.include.xml#L131).

The mod appends a delayed action to native resettle quest 153262's OnQuestEnd (source lines 57–86). After 1000 ms it registers 1500001103. The native quest's existing OnQuestEnd unregister of trigger 153263 remains present; the offline patch verifies that this is an addition, not replacement of the native action list. This is not a generic save-load event: the author's comments report an exceptional quest ending when loading during resettlement, plus ordinary endings where the same cleanup is harmless.

The manually registered trigger gates on positive Human0 marker 1500001613. Its bundled WhichPlayer 1.091 defines that as an initially locked UnlockableAsset; initializer trigger 1500001672 executes checkhuman_serp.lua, which maps PID 0–3 to their synchronized unlocks. Thus the marker's default lock is a readiness boundary; the cleanup cannot assume it was true at initial registration. XML processing Human0 coordinates this **XML delete action**; that is not proof that a Lua action would run on only one Coop client.

The sole child is optional. It checks Harlow RuinCount at least one for harbor 100681; its counter uses exported defaults Global/Current and explicit CheckSpecificParticipant=1. If true, ActionDeleteObjects immediately removes the labeled PirateHarlowResettleGroup in session 180023 (ShipsLeaveMapFirst=0). Native 153262's prebuilt destroy objective uses that same group label; the related native spawning trigger supplies it. If the harbor has been repaired, the optional leaf need not hold the parent open. If the fleet was already destroyed, the delete can have no matching objects. This explains the source's "defuse" intent using the documented optional **child** pattern.

This file's separate pre-spawn cleanup uses GUID+Neutral rather than the group label because the source observed label/owner interaction and repeated fleet-init invocations. It is a different cleanup, not evidence that this quest-end action should be rewritten. The selected trigger has no explicit reset or permanent mod-presence guard; it is not a model for every-save-load initialization or guaranteed safe behavior after removal. For repeated native quest invocations, Serp confirms XML registration does nothing while this trigger is active and can start it again after full completion. This is consistent with conditional repeated cleanup; it is not an every-save-load signal.

## 1500004302 — Campaign in Coop

**Classification: explainable synchronized start/completion protocol; source-qualified movie timing/MP limits remain.** Source: `Campaign in Coop (Serp)/data/config/export/main/asset/AntiDesync/MovieUnlocks.include.xml:223` [GitHub](https://github.com/Serpens66/Anno-1800-Mods/blob/88821b04ee972424667178d35a5080a753a853d0/YouKnowWhatYouDo-Mods/Campaign%20in%20Coop%20%28Serp%29/data/config/export/main/asset/AntiDesync/MovieUnlocks.include.xml#L223).

This FeatureUnlock is initially unlocked, AutoSelfUnlock=0, UsedBySecondParties=0 and inherits AutoRegisterTrigger=1. The input signal is **another asset**, 1500004391: ConditionEvent GUIDLocked, not a negated state check on its own identity. It does not use MovieFinished. The owning 1500004302 later supplies the completion signal by being relocked; do not merge input and output identities.

The notification buttons for native quest 150810/8452 are modified in ADMovies.include.xml:105–122. Choosing play runs RelockNet(1500004300) and RelockNet(1500004391); skip/default runs RelockNet(1500004300) and RelockNet(1500004332). ActiveCallback checks the shared availability identity 1500004300 provided by StoryQuestsInCoop. This is local UI input submitting synchronized commands, not a local MovieFinished event controlling saved progress. The author's host/single-decision caveat still applies; availability is not documented here as an atomic resolution of simultaneous conflicting clicks.

On the play edge, 1500004302 unregisters the skip trigger 1500004332, invokes the slow-speed script, enqueues movie copy 1500004202 with SuppressGamePause=1, relocks 1500004234, and schedules normal-speed script plus Relock(1500004302) after 219000 ms. The movie copy derives from native Video 600170; its actual Video/VideoSubtitle owning record was inspected. Comments report using SuppressGamePause to prevent skipping after CanBeSkipped failed; this is the author's test boundary, not a new movie-engine finding.

The Story dependency supplies both game-speed scripts through the file overlay. **Both current files contain only comments**, so these ActionExecuteScript entries currently make no game-speed change. Missing files in the parent package are not broken references in this declared bundled dependency. A filename cannot establish the behavior of a script. The later [caller/history investigation (local workspace only)](../../../CodeReview/Campaign-in-Coop-Serp/evidence/movie-speed-callers.json) found 18 play-trigger callers and existing author warnings about low-speed coroutine timing and multiplayer exit behavior. Both scripts were already commented in their first Git revision; inactivity alone is not a confirmed defect, and they remain disabled.

The 1500004234 edge is consumed by patched native 150721: its old NotificationRemoved listener becomes GUIDLocked; its new action list enters already-loaded session 180023 after 1000 ms, unlocks PrologueCompleted 142310 and restores selected object visibility. The 1500004302 completion edge is consumed by patched 150594/150836. Native 150594 contains ActionUnloadSession(180014); this is why source comments say 1500004302 unloads the previous session **indirectly**. The movie trigger itself has no unload action.

These dependencies make the configured sequence intelligible without interpreting comments as literal action lists. A fixed 219000 ms completion delay remains a specific movie workaround, not proof that all videos always end at that delay. Later save migration 1500004385 unregisters and, after 1000 ms, re-registers the movie/skip instances. Serp now confirms that fresh registration captures current code, resolving the old saved-code-refresh TODO at the mechanism level. This does not independently prove correct quest progress, listener timing or preservation of every already-completed movie state. Campaign 1.021 is described for Coop with one human slot, with the real Story 1.031/SingleHuman integration; this is not a general four-participant campaign recipe.

## 1500004332 — Campaign in Coop

**Classification: explainable skip protocol; event ordering and shared migration limitations remain.** Source: `MovieUnlocks.include.xml:352`.

This is a separate initially unlocked FeatureUnlock, AutoSelfUnlock=0 and UsedBySecondParties=0, listening for its own GUIDLocked edge. The notification's skip/default command emits that edge after using the same shared availability identity as play. Therefore the selected ConditionEvent is **not itself a local UI event**: local UI submits the RelockNet command, and the listener follows the synchronized game signal.

It unregisters the play trigger 1500004302, relocks 1500004234 to initiate the same 150721 old-world transition, then waits 4000 ms before relocking 1500004302 as the shared completion signal. Unregistering 1500004302 suppresses its **play listener**; it does not delete its Locked property or prevent another trigger from listening to that asset's later relock. No ActionPlayMovie occurs on this path.

The source comment at lines 404–406 requires this completion delay to exceed 150721's transition delay. The effective patched 150721 waits 1000 ms; 4000 exceeds it. The later patched 150594 can then unload 180014. These values are consistent with the documented order dependency, but neither arithmetic nor the offline evaluator proves every session transition finished or prevents every crash. The source still says "seems"/"maybe a delay helps" and that qualification remains.

Like the play path, this depends on listeners already armed, the shared availability resource, retained native consumers and the saved-instance migration guards and registration timing. It has no embedded repeating reset and should not be generalized into an always-rearmable movie UI helper without the corresponding saved-state contract.
